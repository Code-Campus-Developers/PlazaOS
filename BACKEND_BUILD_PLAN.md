# Plaza OS — Backend Build Plan

**Sources:** [PRODUCT.md](PRODUCT.md), [README.md](README.md), [AUDIT.md](AUDIT.md), and the actual frontend contract already encoded in `src/lib/services/*.ts`, `src/routes/admin/**/data.ts`, and the `// TODO: ... once the backend is reachable` comments scattered through `src/routes/admin`.
**Scope:** A new, separate backend project — Next.js (API routes only, no pages) + MongoDB, run as a persistent Node server. This repo (`plaza-os-frontend`) stays frontend-only; this document plans the backend so it can be built in its own repo/folder and wired in by swapping mock data / dev fallbacks for real `api.*` calls, with no frontend contract changes required.
**Non-goals:** No frontend code changes are part of this plan (the frontend already treats every endpoint below as its target contract — see the `TODO` comments in `src/routes/admin/**/data.ts` and the real `api.*` calls in `src/lib/services/*.ts`). No new roles, routes, or features beyond what `PRODUCT.md` describes.

---

## 0. Why this contract, not a new one

The frontend was built "backend-shaped": every admin `data.ts` module's doc comment states the exact future endpoint it mirrors, and every tenant service already calls a real path via `api.ts` (falling back to mock data only in dev). This plan does not invent a new API design — it fills in the backend that makes those exact calls succeed. Endpoint paths, query params, and response shapes below are taken directly from that existing code, not guessed. Where the frontend hasn't committed to a shape yet (e.g. admin write endpoints only sketched as a comment), this plan proposes the most consistent option and flags it as a decision, not a fact.

## Phase 0 — Project setup & foundations

- [x] **Scaffold a new Next.js project** (API routes only — `pages/api` or the `app/api` route handlers, no rendered pages) in its own repo, per `PRODUCT.md`'s architecture section. — done in `backend/` (App Router, `app-api` template, no pages).
- [x] **Configure it to run as a persistent Node server**, not a serverless/edge deployment (`next start` behind a process manager, not Vercel's default serverless functions) — the API itself is a long-running process regardless of scheduler choice, per `PRODUCT.md`. — `npm run build && npm start` runs `next start -p 4000`; no serverless/edge config used. **Deployment target: Railway** (not Vercel) — see [§8](#8-reminders--scheduled-jobs) for why reminder scheduling uses Railway Cron hitting an HTTP endpoint rather than an in-process `node-cron` timer.
- [x] **Add MongoDB connectivity** via `mongoose`, with a cached-connection helper appropriate for Next.js's module reuse across API routes (a single `dbConnect()` used by every handler, connection cached on the global object to avoid reconnect storms). — `backend/src/lib/db.ts`.
- [x] **Set up environment config**: `.env.example` with at least `MONGODB_URI`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `PORT`, `CORS_ORIGIN` (the frontend's dev/prod origins), Paystack keys (see [§7](#7-payments--gateway-integration)), Cloudinary keys (see [§6](#6-file-uploads--receipts)), admin-bootstrap/cron secrets (see [§8](#8-reminders--scheduled-jobs)/[§9](#9-notifications--email)). — `backend/.env.example` has all of the above, plus `RESEND_API_KEY`/`RESEND_FROM_EMAIL` reserved ahead of time (see [§13](#13-open-decisions-not-yet-answered-in-the-brief) — provider decided, send integration itself still deferred until §9 is built).
- [x] **CORS**: allow only the known frontend origin(s) from `CORS_ORIGIN`, with credentials as needed — do not default to `*`. — `backend/src/lib/cors.ts`.
- [x] **Global middleware**: JSON body parsing, request logging, a consistent error-handling wrapper (see [§10.2](#102-error-response-shape)), and security headers (`helmet`-equivalent for Next.js API routes). — `backend/src/lib/route-handler.ts` (`withErrorHandling` + request logging) and `backend/next.config.ts` (`headers()`).
- [x] **Linting/formatting**: match the frontend's conventions where reasonable (TypeScript strict mode, ESLint) so both repos feel consistent to contributors moving between them. — `backend/eslint.config.mjs`, strict `tsconfig.json`.
- [x] **Admin bootstrap, kept separate from fake dev data**: `scripts/bootstrap-admin.ts` creates/updates the one real admin account from `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_NAME` env vars (idempotent upsert, safe to run in any environment including production, never deletes data) — run via `npm run bootstrap:admin`. Never hardcodes an admin password in source; the real credential lives only in the deployment's env vars. See [§13](#13-open-decisions-need-an-explicit-answer-beforewhile-building) for the seed-safety decision this responds to.
- [x] **Seed script, dev/test-only**: `scripts/seed.ts` populates MongoDB with FAKE data shaped like `src/routes/admin/data/mockData.ts` (units/tenants/payments/maintenance/announcements/reminders/calendar events), so local frontend dev against the real backend looks identical to today's mock-data experience. Refuses to run when `NODE_ENV=production`; only ever clears `role:'tenant'` users (never touches the real admin created by `bootstrap-admin.ts`); requires an admin to already exist (errors out with instructions otherwise); tenant password comes from `SEED_TENANT_PASSWORD` or a randomly generated one printed to the console, never a hardcoded literal in source. — `backend/scripts/seed.ts` (run via `npm run seed`).

## 1. Data models (MongoDB / Mongoose)

All enums below use the **shared, already-reconciled** types from the frontend's [src/lib/types.ts](src/lib/types.ts) and `src/routes/admin/data/types.ts` — the backend must not reintroduce the `'closed'` vs `'resolved'` or `'failed'` vs `'overdue'` mismatches that [AUDIT §3.3](AUDIT.md#33-data-model-mismatches-between-the-admin-and-tenant-halves) already flagged and the frontend already fixed.

- [x] **`Unit`**

  - Index on `unitNumber`, `status`, `floor` — `backend/src/models/Unit.ts`

  - Index on `tenantId`, `unitId`, `status`
- [x] **`RentCharge`** — a single billed rent period for one tenant, distinct from `Payment` (a transaction attempt) and `Lease` (the agreement it's billed under)
  - `_id`, `tenantId` (ref `User`), `unitId` (ref `Unit`), `leaseId` (ref `Lease`), `period` (e.g. `"2026-08"`), `amount`, `dueDate`, `status: 'upcoming' | 'due' | 'overdue' | 'paid'`, `createdAt`, `updatedAt`

- [x] **`Payment`**

  - Index on `tenantId`, `status`, `date`, `gatewayReference`, `rentChargeId`
- [x] **`MaintenanceRequest`**
  - `_id`, `tenantId` (ref `User`), `unitId` (ref `Unit`), `title`, `description`, `category?`, `status: 'open' | 'in_progress' | 'resolved'`, `priority: 'low' | 'medium' | 'high'`, `images: [{url, publicId}]` (Cloudinary-hosted — see [§6](#6-file-uploads--receipts); superseded the original single `imageUrl?` sketch above once local-disk storage was replaced with Cloudinary), `notes?`, `createdAt`, `resolvedAt?`
  - Index on `tenantId`, `status`, `priority` — `backend/src/models/MaintenanceRequest.ts`
- [x] **`Announcement`**
  - `_id`, `title`, `body`, `important: boolean`, `audience: 'all' | 'selected'`, `audienceTenantIds: ObjectId[]`, `author` (display string, not a `User` ref), `createdAt`
  - `backend/src/models/Announcement.ts`
- [x] **`Reminder`**
  - `_id`, `title`, `message`, `type: 'automatic' | 'manual'`, `target: 'tenant' | 'group' | 'everyone'`, `targetTenantIds?: ObjectId[]` (for `group`/`tenant`), `targetLabel` (denormalized display string), `scheduledFor`, `status: 'scheduled' | 'sent' | 'failed'`, `sourceRentChargeId?` (ref `RentCharge`, sparse unique index \u2014 set only on reminders auto-created by the rent-due/overdue sweep, see [\u00a78](#8-reminders--scheduled-jobs))
  - Index on `status`, `scheduledFor` — `backend/src/models/Reminder.ts`
- [x] **`CalendarEvent`**
  - `_id`, `title`, `type: 'rent_due' | 'lease_renewal' | 'reminder' | 'other'`, `date`, `relatedLabel?`, `relatedId?` (loose ref back to a `Reminder`/`Payment`/lease, depending on `type`)
  - Index on `date`, `type`
  - **Decided:** this collection only stores genuinely standalone events with no other source of truth. Rent-due and lease-renewal dates are **not** duplicated here — `GET /tenant/calendar` derives `rent_due` items from `RentCharge.dueDate` and `lease_renewal` items from `Lease.endDate` (and `reminder` items from scheduled `Reminder` docs) at read time, merging them with any real `CalendarEvent` docs. See `backend/src/app/api/tenant/calendar/route.ts`.
- [x] **`Notification`** (one collection, `audience: 'admin' | 'tenant'` field distinguishes the two feeds so `/tenant/notifications` and `/admin/notifications` are simple filtered queries against it)
  - `_id`, `audience: 'admin' | 'tenant'`, `recipientId?` (ref `User`; null/omitted for "all admins" or "all tenants" broadcast notifications), `type` (tenant: `'payment' | 'maintenance' | 'announcement' | 'appointment'`; admin: `'payment' | 'maintenance' | 'announcement' | 'reminder'` — matches `NotificationType`/`AdminNotificationType` already defined in [notificationService.ts](src/lib/services/notificationService.ts) and [adminNotificationService.ts](src/lib/services/adminNotificationService.ts)), `title`, `body?`, `date`, `read: boolean`
  - Index on `audience`, `recipientId`, `read`, `date`

**Decided:** single collection with an `audience` discriminator, exactly as modeled above (`backend/src/models/Notification.ts`) — no separate `tenant_notifications`/`admin_notifications` collections. Critically, every read/write query filters by **both** `audience` *and* `recipientId` (never `audience` alone) so a broadcast (`recipientId: null`) notification for "all tenants" can never leak into another tenant's private feed and a tenant can never mark another tenant's notification as read — see `backend/src/app/api/tenant/notifications/**` and `backend/src/app/api/admin/notifications/**`, all of which scope by `recipientId: auth.sub` (tenant) or `{ recipientId: null } | { recipientId: auth.sub }` (admin).

## 2. Auth & authorization

- [x] **`POST /auth/login`** — body `{ email, password }` → `{ token, user }`. Verify password with `bcrypt`, issue a signed JWT (`role`, `sub`=user id, expiry from `JWT_EXPIRES_IN`). Matches the exact shape `AuthProvider.login()` already expects (`LoginResponse { token, user }` in [AuthProvider.tsx](src/context/AuthProvider.tsx)). — `backend/src/app/api/auth/login/route.ts`.
- [x] **`POST /auth/set-password`** — body `{ newPassword }`, requires a valid (even `mustChangePassword: true`) token → hash and store the new password, set `mustChangePassword: false`, return `{ success: true }`. Matches [authService.ts](src/lib/services/authService.ts). — `backend/src/app/api/auth/set-password/route.ts`.
- [x] **JWT verification middleware** — every non-`/auth/login` route requires a valid `Authorization: Bearer <token>` header; on missing/invalid/expired token, respond `401` with **no body or a short plain-text message** (the frontend's `api.ts` treats any `401` as "log out and redirect to `/login`" regardless of body content — see [api.ts](src/lib/api.ts)). — `requireAuth()` in `backend/src/lib/route-handler.ts`.
- [x] **Role-based route guards** — a `requireRole('admin')`/`requireRole('tenant')` middleware/wrapper for every route below; admin users must never be able to hit `/tenant/*` routes for another tenant's data and vice versa. — `requireRole()` in `backend/src/lib/route-handler.ts`, used by every route handler; single-resource routes also verify row-level ownership (e.g. `payment.tenantId === auth.sub`).
- [ ] **Tenant account creation** (`POST /tenants`, admin-only, still §3.2 — not yet built) must, when implemented, follow this MVP account-setup approach exactly (this is an intentional, documented MVP compromise, not a long-term ideal):
  - generate the temporary password **server-side only** using the existing `generateTempPassword()` helper (`backend/src/lib/password.ts`) — never accept or trust a client-supplied temp password (the frontend's client-side `generateTempPassword()` in [tenants/data.ts](src/routes/admin/tenants/data.ts) is mock-UI-only and must be deleted once this route exists);
  - hash it immediately with `hashPassword()` (bcrypt, cost 12) before the `User` document is ever persisted — the plaintext must never touch the database;
  - never store or log the plaintext anywhere (no `console.log`, no audit-log field, no analytics event) beyond the one response below;
  - return the plaintext temp password **exactly once**, in the `POST /tenants` creation response body, so the admin UI can display/copy it via `TempPasswordReveal.tsx` — it cannot be retrieved again after that response;
  - set `accountStatus: 'temporary'` and `mustChangePassword: true` so `POST /auth/set-password` (already built) forces a real password before first real use;
  - **do not** email the plaintext password — if/when a signed password-setup-link flow (§9) is added later, it replaces the reveal-once display, it does not supplement it with an emailed plaintext password.
  - `POST /tenants/:tenantId/reset-password` (§3.2) must reuse this exact same generate → hash → reveal-once flow, not a separate implementation.
- [ ] **Password hashing**: `bcrypt` with a modern cost factor (12+); never store or log plaintext passwords, including temporary ones, beyond the single creation-response return.
- [ ] **No public registration endpoint** — per `PRODUCT.md`, accounts are admin-created only; do not add a `POST /auth/register`.
- [x] **JWT lifetime + refresh strategy — decided as an explicit MVP compromise, not a production-ideal auth architecture**: a single, relatively long-lived JWT (`JWT_EXPIRES_IN=14d` in `backend/.env.example`, read by `signToken()` in `backend/src/lib/jwt.ts`), sent as a Bearer token in the response/request body (not a cookie) and stored client-side by `AuthProvider`. **Why no refresh-token flow today:** the frontend has no refresh-token/silent-renewal logic at all — adding one now would mean building both a backend refresh endpoint and a frontend token-renewal flow neither side currently needs, for an MVP-scale tenant/admin count where a 14-day session is an acceptable tradeoff. **Expected behavior on expiration:** `verifyToken()` throws, every route's `requireAuth()`/`requireRole()` turns that into a `401`, and the frontend's `api.ts` already treats any `401` as "clear the token, redirect to `/login`" — there is no broken/half-authenticated state, just a forced re-login. **This is deferred, not forgotten:** refresh-token/session hardening (shorter access tokens + rotating refresh tokens, or server-side session revocation) is explicitly out of scope for this plan and should be revisited if/when session length or token-theft blast-radius becomes a real product concern — do not build a refresh-token flow speculatively before that need is confirmed.

## 4. Pagination, filtering & sorting contract

- [ ] Every list endpoint accepts `page` (1-based) and `pageSize` query params and returns `{ data, total, page, pageSize }` (admin endpoints) or `{ data, total }` (tenant endpoints, matching what those services already destructure) — **never** just a bare array for a paginated resource, so the frontend's existing `total`/`hasMore` logic ([Phase 3 of FRONTEND_CLEANUP_PLAN.md](FRONTEND_CLEANUP_PLAN.md)) keeps working unchanged.
- [ ] `search` does a case-insensitive substring match on the same fields the mock `data.ts` filters already use (e.g. unit number for units, name/email for tenants) — implement via a MongoDB text index or a `$regex` filter for small collections; a plaza's data volume doesn't need Atlas Search.
- [ ] `sortBy`/`sortDir` accept exactly the field names already used client-side (e.g. `unitNumber | floor | sizeSqft | monthlyRent | status` for units) — reject unknown `sortBy` values with a `400`, don't silently ignore them.
- [ ] Enum-valued filters (`status`, `priority`, `method`, `type`, `rentStatus`, `accountStatus`) accept `'all'` as "no filter" (matching every `data.ts` default) in addition to the real enum values.

## 5. Validation & data integrity

- [ ] **Schema-validate every request body** (recommend `zod`) against the exact shapes in [§3](#3-api-route-map) before touching the database — reject with `400` and a clear message on any mismatch.
- [x] **Business-rule validation**, not just shape validation:
  - Tenant creation only allows assignment to units with `status: 'vacant'`; assigning marks the unit `occupied` and links `tenantId` in the same transaction (mirrors the two-call pattern already in `TenantNew.tsx`: create tenant, then `updateUnit`). — `POST /tenants` (`backend/src/app/api/tenants/route.ts`) checks `unit.status === 'vacant'` inside the transaction and rejects with `409` otherwise.
  - A unit cannot be deleted/reassigned while it has an active tenant without an explicit unassign step.
  - `Payment.amount` must be positive; reject zero/negative amounts.
  - Maintenance request `priority`/`status` transitions are admin-only; tenants can create and read their own requests but never set `status`/`priority`/`notes` directly.
  - `Announcement.audience === 'selected'` requires a non-empty `audienceTenantIds`.
  - `Reminder.target === 'group'` requires `groupTenantIds`; `target === 'tenant'` requires exactly one tenant id.
- [x] **Use MongoDB transactions** (multi-document, e.g. tenant-create + unit-update, or payment-create + notification-create) where a partial write would leave data inconsistent. — `POST /tenants` wraps `User.create` (tenant) + `Unit.save` (occupied/`tenantId`) + `Lease.create` in one `mongoose.startSession().withTransaction()` call: if any step throws, nothing commits — never a tenant with no unit link, a unit marked occupied with no lease, or a lease for a tenant that failed to be created. A prior tenant's lease is never mutated/overwritten on reassignment — each assignment creates a new `Lease` document, preserving lease history. **Caveat:** transactions require a MongoDB deployment running as a replica set (the default for Atlas/most managed MongoDB, including typical Railway-hosted MongoDB) — a bare standalone `mongod` does not support them.

## 7. Payments & gateway integration

- [x] **Choose a payment gateway** — Paystack, using the Initialize Transaction API (hosted redirect page, `authorization_url`) as the simplest MVP integration style. No official SDK is used — a hand-rolled `backend/src/lib/paystack.ts` wraps `fetch`/`node:crypto` directly.
- [x] **`POST /tenant/payments` flow**: the tenant sends `{ rentChargeId }` (never a raw amount); the route loads the tenant's own `RentCharge` by id, verifies ownership and that its `status` is `'due'`/`'overdue'` (rejecting an already-`'paid'` charge with 409, an `'upcoming'` one with 400), creates a `Payment` with `status: 'pending'`, `method: 'gateway'`, `amount` copied from the trusted `RentCharge` (never the request body), then initializes a Paystack transaction (`backend/src/lib/paystack.ts` + `backend/src/app/api/tenant/payments/route.ts`). Responds `{ success: true, id, checkoutUrl }` only once the transaction was actually initialized — if the Paystack call throws, the just-created `Payment` is deleted and a 502 is returned instead of a fabricated success, fixing the trust issue [AUDIT §3.1](AUDIT.md#31-tenant-services-silently-swallow-all-api-errors-and-substitute-fake-data). The frontend (`PaymentsNew.tsx`) redirects the browser to `checkoutUrl` via `window.location.href` rather than navigating straight to the payments list, since the payment isn't confirmed until Paystack redirects back and the webhook fires.
- [x] **`GET /tenant/rent-charges`** (`backend/src/app/api/tenant/rent-charges/route.ts`) lists the authenticated tenant's own non-`paid` `RentCharge` documents, sorted by due date — the trusted source the frontend uses to pick which `rentChargeId` to pay.
- [x] **Webhook endpoint** (`POST /webhooks/payment-gateway`, `backend/src/app/api/webhooks/payment-gateway/route.ts`) receives Paystack's `charge.success` event and calls the shared `settlePaymentByReference(reference, 'paid')` helper (`backend/src/lib/settle-payment.ts`), which settles the matching `Payment` (found via `gatewayReference`) to `paid`, transitions the linked `RentCharge` to `paid`, and creates the matching tenant + admin `Notification` documents via `backend/src/lib/notify-payment.ts`.
- [x] **Reliable failed-payment detection** (`GET /tenant/payments/verify?reference=`, `backend/src/app/api/tenant/payments/verify/route.ts`): Paystack doesn't reliably deliver a webhook for a failed/abandoned one-off charge, so a still-`pending` `Payment` can't rely on the webhook alone to ever leave `pending`. Instead, the frontend calls this route when Paystack redirects the tenant back (`Payments.tsx` detects a `?reference=` query param on mount); the route re-checks the real status via Paystack's Verify Transaction API (`verifyTransaction()` in `backend/src/lib/paystack.ts`) and calls the same `settlePaymentByReference()` helper with `'paid'` or `'failed'` — guaranteeing a failed transaction is explicitly marked `failed` rather than left `pending` forever, and never marks its `RentCharge` paid.
- [x] **Verify webhook signatures** via HMAC-SHA512 of the raw request body (`request.text()`, read before any JSON parsing), keyed with `PAYSTACK_SECRET_KEY`, compared with `timingSafeEqual` against the `x-paystack-signature` header — an invalid/missing signature returns 400 without processing the event body.
- [x] **Idempotency**: both the webhook and the verify route funnel through `settlePaymentByReference()`, which keys updates on `Payment.gatewayReference` and only ever transitions a payment that is still `status: 'pending'` — re-delivered webhook events or a repeated verify call on an already-settled payment are no-ops, and a failed payment can never retroactively mark its `RentCharge` paid.
- [x] **Admin offline payments** (`POST /payments`, `backend/src/app/api/payments/route.ts`, body now `{ rentChargeId, method, date, note }`, `method` restricted to `'cash' | 'bank_transfer' | 'check'`): loads the referenced `RentCharge` (404 if missing, 409 if already `'paid'`), derives `tenantId`/`unitId`/`amount` entirely from that trusted `RentCharge` (never the request body), creates the `Payment` directly as `status: 'paid'` with `rentChargeId` set, flips the `RentCharge` to `'paid'`, sets `recordedBy` to the acting admin, and creates the same tenant + admin `Notification` documents as the gateway path. No bare `tenantId`/`amount` fields are accepted anymore — every offline payment must reference a real rent charge. Not yet wired into the admin `PaymentNew.tsx` UI (that frontend wiring, including a rent-charge picker, is §3.2/build-order step 5 territory).
- **Caveat**: this sandbox has no real Paystack account/keys, so the integration has been verified via `backend/`'s `lint`/`typecheck`/`build` (all clean, all new routes present in the build's route list) and `frontend/`'s `build`/`lint`, but not via a live end-to-end transaction against Paystack's servers. `PAYSTACK_SECRET_KEY`/`PAYSTACK_CURRENCY`/`FRONTEND_URL` are documented in `backend/.env.example`.

## 8. Reminders & scheduled jobs

- [x] **Scheduler decision: Railway Cron, not `node-cron`.** The backend deploys on Railway, which has no persistent always-warm process guarantee across deploys/restarts the way an always-on VM does, and ships a first-class Cron Job feature (an HTTP trigger on a schedule) — there's no strong project-specific reason to keep a `node-cron` timer alive inside the API process when Railway can trigger the same work externally and more reliably (survives redeploys, visible run history, no missed ticks from a process restart mid-sweep). `PRODUCT.md`'s original "runs in-process" framing is superseded by this Railway-specific decision; see [§13](#13-open-decisions-need-an-explicit-answer-beforewhile-building).
- [x] **Reusable plain function**: the actual reminder-processing logic lives in `processReminders(now: Date = new Date())` (`backend/src/lib/process-reminders.ts`) — a plain async function with no scheduler dependency, so it's callable from the cron-triggered HTTP route, a test, or a manual run identically.
  - Finds `Reminder` documents with `status: 'scheduled'` and `scheduledFor <= now`.
  - Atomically claims each one via `findOneAndUpdate({ _id, status: 'scheduled' }, { status: 'sent' })` before sending, so a concurrent/restarted run can't double-send.
  - Creates a tenant `Notification` per `targetTenantIds` (or a single broadcast tenant notification when `target === 'everyone'`) plus one admin `Notification` summarizing the send.
  - Catches errors per-reminder and flips that reminder to `status: 'failed'` instead of crashing the whole batch; returns `{ sent, failed }` counts.
- [x] **Secured HTTP trigger**: `POST /api/cron/process-reminders` (`backend/src/app/api/cron/process-reminders/route.ts`) calls `processReminders()` and returns its result. Auth is a shared secret (`Authorization: Bearer <CRON_SECRET>`, checked against the `CRON_SECRET` env var — added to `backend/.env.example`), not a tenant/admin JWT, since this is a machine-to-machine call from Railway's scheduler rather than a browser request; no CORS/`OPTIONS` export is needed. Configure a Railway Cron Job to `POST` this path on whatever cadence reminders should be swept (e.g. hourly or daily) with that bearer token set.
- [ ] **Manual reminders** (`POST /reminders`, `type: 'manual'`, still §3.2 — not yet built) are designed to be created with `status: 'scheduled'` and picked up by the same `processReminders()` sweep once `scheduledFor` arrives — one code path for both automatic and manual sends so behavior can't drift between them. `processReminders()` itself already handles `type: 'manual'` reminders identically to `'automatic'` ones (it only reads `status`/`scheduledFor`, not `type`), so once §3.2's `POST /reminders` route exists, no changes to the sweep are needed — only seed data currently creates `type: 'manual'` reminders.
- [x] **Idempotent runs**: the atomic claim-before-send (`findOneAndUpdate` status flip) guards against double-processing regardless of whether the trigger is a Railway Cron retry, an overlapping manual invocation, or a process restart mid-sweep.
- [x] **Failure handling**: a per-reminder `try/catch` flips that reminder to `status: 'failed'` on error (e.g. a future email-send failure) rather than leaving it `'scheduled'` forever or crashing the whole sweep.
- [x] **Auto-create reminders from due/overdue rent**: `createAutomaticRentReminders(now)` (`backend/src/lib/auto-rent-reminders.ts`) scans `RentCharge` documents with `status: 'due' | 'overdue'`, skips any that already have an automatic reminder (`Reminder.sourceRentChargeId`, a sparse-unique-indexed field added for exactly this purpose), and creates one `type: 'automatic'`, `status: 'scheduled'` `Reminder` per remaining charge. Called from `POST /api/cron/process-reminders` immediately before `processReminders()`, so newly-created reminders are swept/sent in the same run. The unique index (not just the `$nin` pre-filter query) is what actually guarantees at most one automatic reminder per charge even under a concurrent/retried cron run — a duplicate-key error from a race is caught and ignored.

## 10. Validation, error handling & security (OWASP-aligned)

### 10.1 Auth & access control
- [x] Every route (except `/auth/login`) requires a valid JWT; every route enforces the correct role (`admin`/`tenant`) **and** row-level ownership (a tenant can only ever read/write their own `Payment`/`MaintenanceRequest`/`Profile`/`Notification` rows — verify `tenantId`/`recipientId` matches the authenticated user on every single-resource route, not just on list routes). **Audited (2026-08-12)** across all 21 route files in `backend/src/app/api/**`:
  - `GET /tenant/payments/:id` — 404s unless `payment.tenantId === auth.sub` (not just role-checked).
  - `GET/POST /tenant/maintenance` — list is scoped to `{ tenantId: auth.sub }`; creation derives `unitId`/`unitNumber` from the authenticated tenant's own `User` record server-side, so a tenant cannot submit a request against another unit by passing a different id in the body (no `unitId` field is even accepted from the client).
  - `GET/POST /tenant/notifications/:id/read`, `mark-all-read` — every query filters by **both** `audience` and `recipientId: auth.sub`, never `audience` alone (see the §1 `Notification` decision above); same pattern mirrored for the admin side with `{ recipientId: null } | { recipientId: auth.sub }`.
  - `GET /tenant/announcements`, `GET /tenant/calendar`, `GET /tenant/rent-charges` — all scoped to the authenticated tenant (own id or broadcast/`null`), never a bare unfiltered `find({})`.
  - Admin-only mutations (`POST /payments`, `GET /payments/:paymentId/receipt`, `GET/POST /admin/notifications/**`) all call `requireRole(request, 'admin')` and reject any tenant-role token with `403`.
  - No gaps found across all routes, including the now-complete §3.2 admin CRUD routes — the same role+ownership pattern is applied consistently. Frontend route protection (`ProtectedRoute.tsx`) is UI-only and is not relied on for any of the above — the backend enforces this independently on every request.
- [x] Rate-limit `/auth/login` and `/auth/set-password` to blunt credential-stuffing/brute-force attempts. `backend/src/lib/rate-limit.ts` — an in-memory fixed-window limiter (documented single-Railway-process MVP tradeoff, same class of decision as §13's JWT-lifetime choice; a shared store like Redis would be needed if horizontally scaled). `/auth/login` limits both per-source-IP (20/5min) and per-targeted-email (5/5min) so neither a single-IP brute force nor a distributed credential-stuffing run against one account slips through; `/auth/set-password` limits per authenticated user id (5/15min). **Fixed (2026-08-14):** `POST /tenants/:id/reset-password` (admin-triggered tenant password reset) had no rate limit at all — an audit found this gap since it's an equally sensitive credential-issuing endpoint; now limited per acting-admin id (5/15min), mirroring `/auth/set-password`'s pattern. Covered by `lib/__tests__/rate-limit.test.ts` and the new `tenants/[id]/reset-password/__tests__/route.test.ts`.

### 10.2 Error response shape
- [x] **Decided:** every route responds with a consistent `Content-Type: application/json` body shaped `{ "message": "..." }` on any non-2xx response — `withErrorHandling()` (`backend/src/lib/route-handler.ts`) turns every thrown `ApiError` (and any unexpected error, as a generic "Internal server error" message) into `NextResponse.json({ message }, { status })`. The frontend's `api.ts` (`extractErrorMessage()`) parses that JSON and falls back to raw text/`response.statusText` for any response that isn't JSON-shaped (e.g. the Paystack-facing webhook route, which is server-to-server and intentionally not wrapped by `withErrorHandling`). A short, user-safe message string only — never a raw stack trace or an unformatted internal blob.
- [x] Never leak internal error details (stack traces, DB error messages, library internals) in a response body — log those server-side only. `withErrorHandling()`'s `catch` block always responds with the generic `"Internal server error"` message for anything that isn't a thrown `ApiError`, and logs the real error via `console.error` server-side only.
- [x] `401` responses should carry no sensitive detail; the frontend already ignores the body entirely and just clears the token and redirects.

### 10.3 Input handling
- [x] Validate and sanitize all inputs (schema validation from [§5](#5-validation--data-integrity) covers most of this) — reject unexpected fields rather than silently ignoring them, especially on `PATCH` endpoints, so a client can't sneak in `role: 'admin'` or `mustChangePassword: false` on an update it shouldn't control. **Audited (2026-08-13):** every one of the 14 `z.object({...})` request-body schemas across `backend/src/app/api/**` ends in `.strict()`, so an unknown key (e.g. `rentStatus` on `PATCH /tenants/:id`) is a validation error, not a silent no-op. `tenants/[id]/__tests__/route.test.ts` has an explicit regression test for this.
- [x] Use Mongoose's parameterized queries (never string-concatenate user input into a raw query) to avoid NoSQL injection. **Audited:** every query builds a plain object filter (Mongoose auto-parameterizes); the only place user-supplied text reaches a `$regex` is via `escapeRegex()` (`lib/list-query.ts`, covered by `lib/__tests__/list-query.test.ts`), which escapes regex metacharacters before use — not injection-vulnerable, but does prevent a user search string from being interpreted as a regex.
- [x] Enforce request body size limits (protects against DoS via huge payloads, especially relevant once maintenance image uploads move to multipart). `withErrorHandling()` (`lib/route-handler.ts`) rejects any request whose `Content-Length` exceeds 100KB (JSON bodies) or 30MB (`multipart/form-data`, sized to fit the existing 5-images-×-5MB upload cap in `lib/uploads.ts`) with a `413`, applied globally to every wrapped route.

### 10.4 Transport & secrets
- [ ] HTTPS-only in production (terminate TLS at the load balancer/proxy or directly, depending on hosting) — Railway terminates TLS at its edge for the deployed domain, so this is inherited from the hosting choice rather than something the app itself configures.
- [ ] All secrets (`JWT_SECRET`, DB URI, gateway keys, `RESEND_API_KEY`) come from environment variables, never committed — mirror the frontend's existing `.env.example` convention.
- [ ] Rotate `JWT_SECRET` capability considered (even if not implemented day one) — don't hardcode it anywhere reachable by a compromised dependency.

### 10.5 Dependency & config hygiene
- [x] Run `npm audit` as part of CI once the backend project exists; don't let it silently accumulate high-severity advisories the way the frontend's dev-tooling chain currently has (see [FRONTEND_CLEANUP_PLAN.md Phase 6](FRONTEND_CLEANUP_PLAN.md)). **Re-checked (2026-08-13):** `backend`'s `npm audit` reports 0 vulnerabilities. `frontend`'s `npm audit` still reports the same 13 high-severity advisories, all tracing to `nanoid` inside the `postcss`/`tailwindcss`/`vite`/`vitest` dev-tooling chain with no fix available upstream — already investigated and accepted as a documented, no-runtime-impact risk in [FRONTEND_CLEANUP_PLAN.md](FRONTEND_CLEANUP_PLAN.md); unchanged since that assessment.
- [x] Keep `CORS_ORIGIN` an explicit allow-list, not a wildcard, since the API accepts credentials (JWT bearer tokens plus, if cookies are ever introduced, cookie-based CSRF exposure would follow). — `backend/src/lib/cors.ts`'s `ALLOWED_ORIGINS` is built from the comma-separated `CORS_ORIGIN` env var; `withCors()` always echoes back one of those exact origins (or the first allow-listed one), never `*`. Confirmed correct for a Railway-hosted API talking to a separately-hosted Vite/React frontend — the frontend's production origin just needs to be added to `CORS_ORIGIN` alongside the local dev origin.

### 11.1 Cleanup-plan: issues found during the 2026-08-14 audit, deferred rather than fixed

A full manual read-through of all 34 route files and 18 `lib/*.ts` files (cross-checked against an automated exploration pass) found one real, safe-to-fix bug (see §10.1's rate-limit fix above) and the following lower-priority items, intentionally left as documented future work rather than fixed in this pass — each would either risk a breaking change to the frontend contract or needs a more careful, dedicated pass than a drive-by fix:

- **Date-field format validation gap.** `date`/`scheduledFor`/similar fields across `calendar/route.ts`, `reminders/route.ts`, and `payments/route.ts` (POST) are validated as bare `z.string().min(1)` — any non-empty string is accepted, not just an ISO-8601 date. Not currently exploitable (nothing parses these with `new Date()` in a way that would silently corrupt data beyond a garbage display value), but worth tightening to `z.string().regex(/^\d{4}-\d{2}-\d{2}/)` (or `z.iso.date()` if upgrading to a newer Zod) in a future pass — deferred because the existing seed data and any already-stored records haven't been audited for conformance, so tightening validation now could reject legitimate-but-differently-formatted existing data.
- **`rent-charges` `tenantId` query param has no format validation.** `GET /rent-charges` accepts `?tenantId=` with no check that it's a well-formed Mongo `ObjectId`; an malformed value just yields zero results from Mongoose (not an error, not a security issue — the query is still parameterized), but a `400` would be a better developer-facing signal than a silent empty list. Low priority, deferred.
- **Bare-array vs. paginated-envelope inconsistency.** `tenant/notifications` and `admin/notifications` (`GET`) both return a raw array, while every other list route in the API returns the `{data, total, page, pageSize}` envelope described in [§4](#4-pagination-filtering--sorting-contract). This was almost certainly intentional (notification lists are typically short and rendered as a dropdown/bell-icon panel, not a paginated table), but it's a documented contract inconsistency. **Deliberately not changed** — the frontend's `useNotifications.ts`/`useAdminNotifications.ts` hooks are written against the bare-array shape today, so converting it would be a breaking frontend change requiring a coordinated update on both sides, not a backend-only cleanup.
- **`maintenance/[id]` `resolvedAt` auto-set behavior.** `PATCH` only auto-sets `resolvedAt` to today when the request omits it **and** the status transitions to `resolved`; an explicit `resolvedAt: null` in the body overrides this and leaves it unset. This is intentional (lets an admin explicitly clear a resolution timestamp), not a bug, but is subtle enough to be worth calling out here — covered by `maintenance/[id]/__tests__/route.test.ts`'s explicit-null-override test.

## 12. Deployment & operations

- [ ] **Deploy on Railway** as a long-running Node process (`npm start` → `scripts/start.js` → `next start -p $PORT`, falling back to `4000` locally) — Railway's own restart policy supervises the API process; reminder scheduling does **not** depend on this process staying warm, since it's triggered externally by a Railway Cron Job hitting `POST /api/cron/process-reminders` (see [§8](#8-reminders--scheduled-jobs)), so a missed tick from an API restart is no longer possible. The Railway service's **Root Directory must be `backend/`** so that `backend/railway.json` (start command + health-check path) and `backend/package.json` are picked up. Not yet deployed — this sandbox has no Railway project/credentials to actually provision.
- [ ] **Configure a Railway Cron Job** to `POST /api/cron/process-reminders` with `Authorization: Bearer <CRON_SECRET>` on the desired cadence (e.g. hourly), pointed at the deployed backend's URL. Requires a live Railway deployment first.
- [x] **Structured logging** (request id, route, status, latency; separate error log stream) — `withErrorHandling()` (`backend/src/lib/route-handler.ts`) now logs one JSON line per request (`{requestId, method, path, status, durationMs}`), tagging the response itself with an `X-Request-Id` header so a client-reported error can be correlated back to the exact log line. Any `status >= 500` (including unexpected/unhandled errors) is written to **stderr** (`console.error`) with the raw error object attached; everything else goes to **stdout** (`console.log`) — a genuinely separate stream a log viewer (e.g. Railway's) can filter on independently, enough to debug a failed payment or missed reminder after the fact without reproducing locally.
- [x] **Health check endpoint** (`GET /api/health`) for the process manager/load balancer. — `backend/src/app/api/health/route.ts`: unauthenticated, no CORS/`withErrorHandling` wrapper (a health probe shouldn't need a Bearer token or worry about browser CORS), calls `dbConnect()` and reports `{status:'ok'|'degraded', db:'connected'|'disconnected'}` with `200`/`503` based on `mongoose.connection.readyState`. The route lives under `src/app/api/`, so the served path is `/api/health` — every route in this backend is under `/api`; there is no top-level `/health` path.
- [x] **Database backups for MongoDB** (this holds every tenant's payment history — treat backup/restore as a hard requirement, not a nice-to-have). **Decided:** rely on the managed MongoDB provider's built-in automated backups (MongoDB Atlas's continuous/scheduled backups, or Railway's MongoDB plugin backup feature) rather than a custom `mongodump` script/cron — no self-hosted standalone `mongod` in production. This is a provisioning-time decision to make when the real database is created, not something this sandbox (no real MongoDB deployment) can configure or verify.
